Branch `feature/4.0-phase1-browser`, tag `checkpoint-before-4.0` (= 3.1, `ad13eec`). Tested 2026-10-22 on macOS 26.6.2, Apple Silicon.

Isolation:
- All tests ran in throwaway instances: own history folder, own downloads folder, the queue paused, and a dedicated WebKit data store per instance.
- The test builds lived in a temporary folder; the installed 3.1 app was never replaced.
- Afterwards, the production library was checked unchanged: 1 video, 1 job, `quick_check ok`; the downloads folder (8 files) and Trash (40 files) were untouched.

## Recommendation: **GO, with conditions**
WKWebView can be your main YouTube browser. The deciding fact: **signing in with your real Google account worked inside it**, so you get your own YouTube (feed, subscriptions, notifications) rather than a guest copy. Browsing, playback, full screen, YouTube's keyboard shortcuts and in-page navigation all worked.

The conditions are three problems found and fixed in this phase, and two that shape Phase 2:
1. Fixed: the page didn't return to the window after full screen.
2. Fixed: WebKit's own "is media playing?" signal is wrong on YouTube.
3. Fixed: resuming the native player didn't pause YouTube.
4. **Shapes Phase 2:** a WebKit data store can't be deleted while the app session that used it is running.
5. **Shapes Phase 2:** memory per signed-in page is high, which limits how many tabs stay live.

Keep **Open in your browser** one click away, because Google could tighten its embedded sign-in policy at any time.

## Google sign-in findings
- Google's published restrictions target **OAuth inside embedded webviews** ([2021](https://developers.googleblog.com/en/upcoming-security-changes-to-googles-oauth-20-authorization-endpoint-in-embedded-webviews/)) and **sign-in from embedded browser frameworks** such as CEF ([2019](https://security.googleblog.com/2019/04/better-protection-against-man-in-middle.html)).
- **What happened here:** the **normal web sign-in on accounts.google.com** in WKWebView was **allowed**: one account, with a phone-prompt second step, using WebKit's own user agent plus `VideoBuddy/4.0`. Nothing was spoofed or worked around.
- **Not guaranteed:** Google can change this without notice. The app must treat sign-in as "works today", and always offer **Open in your browser** and guest browsing.
- **Credentials:** I never asked for or recorded any. One automated screenshot happened to catch the sign-in screen with your email address. I deleted it immediately; it was never committed or shared.

## Bugs found and fixed in this phase (on the branch)
1. **After full screen the page stayed outside the window.** The container now re-attaches the web view whenever full screen ends (`reattachToken`).
2. **WebKit's `requestMediaPlaybackState` says "playing" on YouTube pages where nothing plays.** It paused your native player at 4.2 s. Coordination now uses a read-only check of the page's audio/video elements, in a separate script world (YouTube's scripts can't see or affect it). Muted previews don't count. WebKit's value is kept for comparison.
3. **Resuming the same native file didn't pause YouTube.** The pause hook now runs at the start of every play.
4. **Two test instances received each other's commands.** `VS_TEST_CHANNEL` now separates them.

## Known limitations
- **Memory:** a signed-in YouTube page uses 0.6–1.4 GB. Four live signed-in tabs could reach several GB. Phase 2 must put background tabs to sleep, and react to macOS memory pressure.
- **Deleting a data store needs a relaunch** if a web view has used it. Clearing the data works at once.
- **Click-to-play was flaky in automation** (2 of 5); human clicks worked. Your check below settles it.
- **The EU consent page couldn't be triggered** in testing.
- **YouTube Premium offline downloads** are only supported in Chrome, Edge, Firefox and Opera, and stay inside YouTube ([YouTube Help](https://support.google.com/youtube/answer/11977233)). Signing in doesn't change that.
- **The offline rules are unchanged** (see the plan, §3C). Downloading YouTube content is only allowed where YouTube authorises it or with written permission, and this app can't verify either.

## Revised plan for Phases 2–5 (changes from the plan in **bold**)
- **Phase 2: tabs, sessions, resources:**
  - as planned: tabs, the ⌘T/⌘W/⇧⌘T/⌃Tab shortcuts, restore after restart and crash, background tabs loading only when opened;
  - **sleeping tabs tuned to the measured memory:** 4 live tabs (D5), but background tabs sleep after 10 min, and immediately under macOS memory pressure;
  - **Sign out & Clear Browsing Data:**
    - clears the data at once;
    - the store itself is deleted on the next launch, before any web view exists (a "pending removal" marker);
    - the deletion is then checked, as required for Fresh Start and Reset;
  - **sign-in persistence across relaunches;**
  - the media check from fix 2 applied to every tab;
  - the "Allow background audio" setting.
- **Phase 3: Watch Later and library links:** as planned (schema v4 + a verified backup, oEmbed metadata, the playlist-page bar).
  - **Plus:** the optional Arc companion (c): a `videobuddy://save?url=` link type and a Raycast command, both small.
- **Phase 4: Offline Hub:** as planned. YouTube content is labelled as needing authorization, and the authorization basis you state is recorded per video.
- **Phase 5: polish and release:** as planned, plus a performance pass with 4 signed-in tabs.
- **Fresh Start (3.2)** is still unbuilt; when it's built, it uses the deferred store deletion from Phase 2.
